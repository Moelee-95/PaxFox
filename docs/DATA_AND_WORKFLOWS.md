# Data rules and workflows

Snapshot: 2026-11-07 / base `eb4d9cf` with local updates. Read this for behavior/storage changes; [APP_MAP.md](APP_MAP.md) locates files/tests. These contracts describe implementation, not the larger original specification.

## State and persistence

```text
Form/dialog -> LedgerStore public method -> validated SQLite transaction
  -> commit -> refresh(): read consistent snapshot -> replace collections/indexes
  -> notifyListeners -> ListenableBuilder updates UI

LedgerIndex -> visited-month summaries + cached type-only filters
  -> first text query builds normalized text -> most recent text-search result
currentBalances -> one ledger pass -> cache until snapshot/local day changes
```

No Provider/Riverpod/BLoC/service locator/router framework. Store is injected through constructors. Snapshot lists/sets are unmodifiable; never mutate them to simulate a write. Failed reads retain the last complete snapshot. The entire active ledger is loaded into memory; list rendering is lazy, database pagination is not implemented. `Totals` is a mutable calculation accumulator, not a persisted entity.

Snapshots prepare monthly reports/rankings and today's account balances before notification. At 1,000+ transactions, transaction decoding and preparation run in a worker; older refresh generations cannot overwrite newer results. The independent `refreshing` notifier drives progress without forcing page rebuilds. Legacy receipt and scanned-batch transaction ID sets are cached with the snapshot, so ordinary transaction forms skip attachment queries. No schema or financial formula changes.

Public writes return success once committed even if the following snapshot reload fails. `snapshotNeedsRefresh` then makes the global `StoreStatus` banner offer Retry and blocks stale UI interactions. Retry reads storage only; it never repeats a payment/import. A successful refresh clears the flag. Initial store-open failure closes its database before exposing startup Retry.

Monthly snapshots index category expenses/refunds in original order and cache category rankings by currency. Invoice preview paths are resolved once per widget; thumbnail decoding uses display height. Extraction progress uses a separate notifier, and base64/request encoding runs in an isolate. The extraction deadline covers preparation, key loading and HTTP together. Connection, timeout, access, quota, server and malformed-response failures retain selected images and offer user-controlled retry, without automatic repeated Gemini requests or exposing provider payloads.

Category name/kind lookup uses a snapshot map (`categoryFor`); icon/color access shares it. `saveCategory` skips transaction/recurring/receipt label rewrites when the trimmed name is unchanged, so appearance-only edits leave ledger update timestamps untouched. Actual renames still cascade atomically. Search caches are scoped to the complete snapshot and are discarded on refresh; lazy text normalization moves its cost to the first nonempty text query. No database pagination or financial rule changed in this optimization pass.

SQLite file: `moneva.sqlite` under `getApplicationSupportDirectory()`. Native sqflite on Android/iOS; SQLite FFI selected for Windows/Linux. Private receipt files use relative `receipts/...jpg` paths beneath the same support directory. Prepared scan copies use an app-owned temporary directory. This layout is not a portable backup format.

This is the logical schema after migrations, not a replacement DDL script. SQL booleans use 0/1; table currency codes use enum names `eur`/`usd`/`gbp`/`iqd`, while invoice JSON uses ISO codes such as `EUR`.

## Financial contracts

| Concern | Required behavior |
| --- | --- |
| Money | Integer minor units, EUR/USD/GBP 2 decimals and IQD 3 decimals; UI displays and money inputs use comma thousands separators and dot decimals. UI parsing accepts grouped values; an unambiguous decimal comma (12,50) is normalized, while 1,234 means one thousand two hundred thirty-four. Strict domain parsing, extraction JSON and CSV serialization keep their existing ungrouped-decimal contract. Grouping never changes stored minor units or currency precision. New amounts positive and at most `9000000000000000` cents. Signed opening balances and invoice line prices have separate handling. |
| Type effects | Expense: source minus, spending plus. Income: source plus, income plus. Refund: source plus, spending minus. Transfer: source minus/destination plus, no income/spending. |
| Assignment | Normal new expenses/income require an account. Historical CSV/bulk unassigned entries count in reports but do not alter balances; edits can retain that state. Refunds may be unassigned. Transfers require two distinct existing accounts in the active reporting currency. Different native currencies require both deducted and received native amounts; same-native-currency transfers move identical native amounts. |
| Availability | Blocked means `available=false`: include in wealth, exclude from spendable, reject expenses/outgoing transfers, allow income/refunds/incoming transfers. |
| Overdraft | Cash never negative; each bank needs explicit overdraft permission. Related writes validate affected accounts' daily balances, including protected historical/future deficits. Bulk operations validate the final combined result. |
| Opening date | New accounts include same-day transactions (`includeOnAsOf=true`); legacy end-of-day snapshots include strictly later dates. Display balances stop at today; reports use selected transaction month, including future dates. |
| Debts | Money owed by user reduces wealth; receivables increase wealth. Neither is spendable cash. Overview and Accounts show separate Debts and Money owed to you sections with their own totals and add controls; the latter defaults new records to receivable. Overview Pay debt/Receive payment opens the transaction editor with the matching protected Debt category, name and full remaining native-currency amount; partial amounts and account selection are supported. Expense or income and outstanding balance update in one transaction. Payment amount edits adjust the difference; deletion restores the settlement, subject to normal funds validation. Overpayment, blocked spending and historical/future deficits reject the whole write. A debt with linked settlements cannot switch direction or currency. Manual debt corrections remain available. Deleting a debt keeps its posted transactions, detaches links and prevents later payment edits/deletion from recreating that debt. |
| Account deletion | Only unused bank accounts can be deleted. Reject source/destination transaction links and recurring rules/history, including archived rules and rows in other currencies. Eligibility is cached in the read snapshot for UI; deletion rechecks all links inside its SQLite transaction. Cash accounts cannot be deleted. Deletion removes the opening balance from wealth; no transaction or rule is deleted. |
| Correction | AccountForm changes opening baseline by desired-current difference, preserving opening date and payments. Changing bank currency converts the opening baseline and linked native effects using exact old/new rates and rounds once per destination native minor unit; it preserves transaction reporting values and original FX snapshots. The requested current balance corrects any aggregate rounding difference. Future recurring rules using the former native currency (including implicit legacy app-currency rules when converting an app-currency bank) adopt the new native currency with converted amounts. Failed occurrences explicitly using the former native currency convert their input amounts/currency; posted history remains unchanged. It is not a reconciliation transaction or independent dated snapshot. |
| Dates | Transaction/schedule days are local calendar `YYYY-MM-DD`. Creation/update times are UTC ISO strings. `createdAt` is displayed locally and preserved unless explicitly edited in Added on beneath Date. Editing it does not change the financial day or amounts; invalid/missing legacy times are omitted. |
| Categories | Built-in Debt categories exist for expense and income, have fixed names/kinds and cannot be deleted (domain/SQL protection); icon/color edits remain available.  Refunds use expense categories; transfer label is fixed. Rename updates matching ledger, recurring, receipt item and legacy receipt-draft labels atomically; original batch extraction JSON remains source history. Icon/color changes do not rewrite money. The catalog offers 113 icons in nine groups, retaining all 92 legacy IDs and adding Material/Font Awesome icons. Persist stable enum names, never glyph codes. Optional colors are opaque ARGB integers (`0xff000000`-`0xffffffff`); omitted color on update preserves the saved value. Null uses a neutral transaction badge; transaction prices independently show red minus for expenses, green plus for income/refunds, blue unsigned for transfers. Refund rows are labeled and transfers use a neutral badge. The full-page editor defaults to mint for expenses or turquoise for income and saves the chosen color. Category colors propagate through category lists, transaction badges, manual category choices and monthly reports. New categories can choose expense/income; existing kind remains fixed. |
| Currency | One currency chosen during first-run setup (EUR/USD/GBP/IQD), committed atomically with accounts/debts/setup marker. Bank accounts may use another supported currency with a positive manually entered exchange rate; cash uses the setup currency. Upgrades keep EUR as the active currency. Other reporting-currency ledger/account records stay stored and excluded from active views; native debt currencies are converted for current display using shared defaults. Never relabel their amounts. Reports use the active currency. Manual expense/income/refund inputs default to active currency and may use the selected foreign bank currency. Recurring inputs default to the selected account currency; each occurrence uses the account rate at successful posting/retry. Invoice review continues using app-currency item values, which post converted native movements when assigned to a foreign bank. CSV preserves reporting amounts and includes native/FX metadata when needed. Changing currency after setup is not exposed. |

Cashflow is an empty placeholder. Its previous plan model, projection engine, form and store API have been removed. Existing `financial_plan` settings are left untouched as unused legacy data; they are no longer read or written.

## Foreign-currency accounting

An account rate is **native major units per one app-currency major unit**: at `1 EUR = 1,772 IQD`, a EUR2.00 expense posts EUR2.00 to spending and deducts IQD3,544.000. An IQD3,544.000 input divides by the same rate and reports EUR2.00. Decimal rates are stored as text, parsed with grouped UI input, and calculated with BigInt rational arithmetic (no floating-point money). Each destination amount rounds once to its currency's minor unit, halfway away from zero. Rates allow up to nine decimal places. Entries too small to produce a positive reporting/native amount are rejected.

Posted `transactions.amount/currency` never change when an account rate changes. `account_amount` and `destination_amount` drive native bank balances; legacy null movements fall back to reporting amount only when the account native currency matches. Wealth/spendable values convert today's native balances at each account's latest rate. Account currency changes atomically convert the native baseline/effects, preserving reporting amounts and original FX snapshots. Historical/future daily overdraft validation still applies in native units; blocked accounts may receive but not spend. No automatic FX gain/loss or transfer fee expense is posted.

Transfers store the user-entered native deduction and receipt independently. The frozen snapshot records both original currencies/amounts and configured valuation rates; history derives the actual received-per-deducted-unit rate from that pair (shown to nine decimal places). Transfers remain excluded from income/spending. Editing a description/category/date retains the original reporting value, native effects and saved rate; changing money/account uses a newly calculated conversion. Recurring rule currency may be app or selected-account currency; failed occurrences retain their own copied input amount/currency and retry at the current account rate. Posted occurrences are never automatically rewritten/reposted.

FX CSV exports retain the existing reporting columns and add `Account currency`, `Account amount`, `Destination currency`, `Destination amount`, `FX details`. Native amounts are human-readable ungrouped decimals; FX details are original snapshot JSON. Import requires matching account native currencies and retains historical reporting/native values even if current configured rates differ. Ordinary nine-column and legacy five-column files remain supported. FX export requires assigned-account metadata; CSV still is not a complete backup.

## Local profile

The More user card reads the local profile from the same complete snapshot. Missing profile settings default to empty strings. `saveProfile` trims and validates name (1-80 characters) and optional email (up to 254 characters) before writing both keys in one SQLite transaction, then uses normal committed-write refresh recovery. Existing settings storage accommodates these keys without a schema migration. Profile fields are not authentication credentials and are not included in invoice extraction requests. Support options in More have no actions yet, by user request.

## Invoice flow and attachment lifetime

1. Camera/gallery/upload adds up to 10 ordered files. Upload accepts PDF and supported image formats. PDFs retain validated `%PDF-` bytes without JPEG conversion; images retain the existing compression path. `InvoiceImagePreparation.prepare` uses the `paxfox/invoice_images` platform channel on Android/iOS: a serial native background worker reads metadata, samples before decoding, applies all EXIF orientations, and encodes JPEG once. It avoids the former PNG intermediate and Dart decode/repeated JPEG encodes. A Dart queue serializes all preparation, including retries/extraction. Generation cancellation skips stale queued jobs and rejects active results before writing. Owned temp JPEGs associate prepared bytes with their `File` objects. Desktop/tests retain a bounded Dart fallback. Extract remains disabled while preparing. The capture screen allows cancellation and times out each page after 45 seconds, stopping the batch; late preparation results are discarded and owned files released. Cancel/timeout invalidate queued work; picker-owned sources remain until active preparation settles so timeout cannot delete a file still being decoded. Gallery shortcut opens this same flow with gallery selection instead of camera.
2. No upscaling; cap short edge 2,000px, long edge 6,000px and total pixels 4,000,000 (floor dimensions). Native JPEG quality is 86 in one pass. Compatible unrotated JPEGs up to 1 MiB pass through byte-identical based on metadata, without decoding. Transparent images flatten to white. Max source 25 MiB; combined prepared upload cap 12 MiB. Soft target is not a guaranteed size or lossless compression.
3. Extractor receives ordered prepared files + categories for the selected expense/income mode; `bytesFor` reuses preparation for upload and later persistence. Request is Gemini `generateContent`, default `gemini-3.5-flash-lite`, override `GEMINI_MODEL` with Dart define. Fetch encrypted config from the saved HTTPS URL (default `https://api.moelee.de/api/v1/gemini-config`) or use the saved manual key when selected; no automatic fallback between sources. Both values are retained when switching. Settings save atomically in existing key/value storage without a schema change. Custom sources must retain the version-1 AES-256-GCM format and bundled encryption material. Send key in `x-goog-api-key`; bundled decryption material is not a server-side secret.
4. Prompt treats receipt text as data, requests actual items/prices/categories/unknowns plus each item’s invoice date, supports multiple invoices (`multiple_invoices` flag), deduplicates overlapping photos and preserves genuine duplicate products. Parse unknown fields for user correction; no auto-save. No offline OCR; PDF uploads use `application/pdf` inline input.
5. Review expands integer quantity into individual quantity-one rows, distributing cent remainders exactly. Fractional/weighted lines remain charged lines. Explicit adjustment becomes a visible editable item. Save total is the reviewed item sum, **not an editable extracted charged-total field**. Missing/mismatched currency requires explicit confirmation of the original app currency; no conversion. Validate merchant/category/items, every item date (legacy single-invoice root date can supply it), and positive net total. Review has a date on each item and in its editor; a multi-invoice missing date never inherits another invoice’s root date.
6. Retain image copies, then commit every nonzero item and its metadata/link atomically: in expense mode positive item -> expense and negative item -> refund. Income mode saves positive items only as income; quantities never split a salary payment. Items use their own invoice dates. Credits are written before gross expenses, then historical/future account balances are validated once against the complete batch so later refunds cannot fund an earlier deficit. No additional invoice-total charge. Failed saves remove newly retained copies and leave no partial batch.
7. Shared source remains reachable from item TransactionForm. Home, All transactions and category detail lists collect visible entries linked to one scanned batch into a shared outlined group with one invoice-number/merchant heading and a count of visible items. Groups are anchored at their first matching entry in the existing result order, retaining internal item order; filters do not bring hidden items back into the list. This is display grouping only: stored dates, reporting amounts, source links and individual edit/selection actions are unchanged. Rows remain lazy even for large batches. Each item can be edited/deleted independently; source files are cleaned when the final linked item is deleted. Legacy `receipts` entries route to invoice review and remain one expense; do not silently split them.
8. Page removal/scan disposal releases only owned preparation files/cache. Never delete gallery originals. Cancel closes the active HTTP client, cancels timers and ignores late responses; isolate processing can finish asynchronously. UI timeout default 180s, configurable 30-900s. Network/config can fail earlier. Persistent orphan sweeping after a crash is not implemented.

Income extraction uses a dedicated prompt for payslips, bank statements and paid customer invoices. Payslips produce one net payment, not gross/tax components. Statements include received-income credits only and exclude debits, own-account transfers, purchase refunds, loan proceeds, balances and summaries. Unpaid invoices are not received income. Every returned income row must be explicitly classified `entry_kind: income`; other/unknown classifications are filtered by the parser. Gemini classification is probabilistic, so review remains mandatory and nothing auto-saves. Negative/zero income and adjustments are rejected by domain validation. Review allows blocked receiving accounts, uses income categories and exposes per-item dates. Draft `entry_type` persists in existing JSON; legacy drafts default to expense and legacy single-expense editing rejects income mode. Shared source links, edit/delete cleanup and atomic rollback apply to both modes.

PDF attachments show a PDF document card rather than image rasterization; their original bytes remain attached. File-picker content streams are copied into owned temporary files with size/timeout checks, prepared into owned scan files, and source copies are removed afterward. Stored PDFs use `.pdf`; images remain `.jpg`. Existing 25 MiB source and 12 MiB combined upload limits remain, including PDFs; unreadable/encrypted/oversized documents may require a clearer/smaller file. Native picker/scanner and live Gemini still require device verification.

Manual pickers may change type; recurring restricts to expense/income. Bulk category changes and scanned review keep their existing type/kind constraints. A picker type switch remains local until a category is chosen (Transfer needs no category). ## Recurring execution

Daily/weekly/monthly/yearly expense/income rules have intervals 1-120 of their selected unit. Weekly rules select Monday-Sunday; monthly/yearly rules select day-of-month and yearly rules also select month. Calendar arithmetic and short-month clamping preserve selected days across DST/leap years. First schedule must be today/later and outside opening snapshot coverage. Ledger checks happen on startup/resume, rule save or Check due payments; pull refresh only reloads storage. Automatic means local bookkeeping, not a real bank payment.

`processRecurring` catches up due dates, up to 6,000 occurrences per check; income precedes expenses on a date. Rule/date uniqueness plus transactional posting prevent duplicates. A failed account/funds check records an unpaid occurrence without a partial charge. Manual rules create a separate durable pending occurrence per due date, without changing money. Confirm uses today's date and the current account rate, retaining scheduled history; failed confirmation leaves it pending. Repeated confirmation cannot post twice. Automatic failures retain Retry/Skip; manual occurrences cannot be skipped. Pause stops generation; resume restarts from the next valid date on/after today. Rule edits affect future occurrences; archive preserves history. Posted entries edited/deleted manually are not recreated. Asset applies only to income, Liability only to expenses; both are stored labels for future features.

Manual notifications expose Add to debts for expenses and Add to money owed to me for income, both in the inbox and native notification actions. Conversion creates one outstanding record and marks that occurrence skipped with a Moved to debts/receivables note, removing it from the inbox/OS reminders. No account funds or income/expense totals change. The original input amount and currency become the outstanding balance. Missing display defaults are seeded from the known selected bank rate; no account money is posted. Future occurrences remain unchanged. The occurrence/debt link prevents duplicate conversions or later recreation after deletion.

The main-header notification bell opens an in-app inbox containing every manual occurrence with failed/unposted status, including those for archived rules. It catches up due rules on opening, sorts pending dates oldest first and has no history-row limit. Each occurrence remains separate until successfully confirmed; confirmation calls the existing idempotent `retryRecurring` path using today and current FX rates. Failed confirmations retain the item/error. The badge updates from store snapshots, and posted items disappear regardless of whether confirmation came from the inbox, Recurring history or an OS action. This requires no additional persisted data or notification permission.

`RecurringNotifications` initializes with the real store in `main.dart` and requests notification permission on startup when the saved notification preference is enabled, even before setup or any recurring rule exists; the OS decides whether to show a prompt for an already answered permission. Startup does not request exact-alarm settings access; saving a manual reminder retains that check. Permission-request failures do not prevent startup. Injected test stores bypass native initialization. Settings saves `notifications_enabled` immediately in existing key/value storage (no schema migration). Disabling cancels all visible/scheduled phone reminders and clears schedule fingerprints; disabled startup skips permission prompts, and saving recurring rules does not request permissions. Enabling requests phone permission and regenerates pending/future reminders; a denied request leaves the switch off with guidance to use phone settings. The in-app inbox, pending occurrences and confirmation/posting behavior remain available. The Settings form keeps all its fields mounted for complete validation while scrolling. Store changes and app resume refresh up to 60 chronological future OS requests across rules, below iOS's 64-request limit. Open the app regularly to extend this window. Stable rule/date IDs resolve through SQLite; foreground and terminated-launch Confirm actions catch up due occurrences before posting. Delivery never posts money. A notification-body tap catches up due occurrences and queues the matched occurrence ID for navigation. MainScreen consumes queued targets after its first frame (including terminated launches), opens the Notifications route, and reuses an already open inbox on later taps. The referenced pending card is pinned first, outlined/tinted and labeled Opened from reminder; other items retain chronological order. Body taps never confirm a payment. The explicit Confirm action keeps its existing posting behavior. Android requests notification/exact-alarm permissions, uses reboot receivers, and falls back to inexact delivery with a warning when exact alarms are disabled. iOS uses foreground confirmation actions. Phone-local IANA time zone is refreshed on open/resume; travel while closed retains the previous schedule until refresh. Android ongoing/autoCancel-false flags discourage dismissal, but Android 14+ and iOS may allow it. Pending database items survive dismissal and notifications are restored on refresh. Permissions, force-stop, power policies and platform limits can prevent/delay delivery. Physical notification delivery and iOS builds need device verification.

## CSV and export scope

New exports use nine columns: `Date,Details,Category,Cost,Notes more info,Account,Type,Destination account,Currency`. One file can include multiple accounts and expense, income, refund and transfer rows. Accounts and transaction types use multi-select cards with All toggles; defaults include every account (including Unassigned) and all types. Selections filter both exports and account-aware imports. A transfer matches either selected account and appears once, retaining both account names.

Account names match existing app accounts case-insensitively after trimming. Blank Account means Unassigned; transfers require distinct source/destination accounts. Unknown/ambiguous names are reported by CSV row; accounts are not created or silently reassigned. Export rejects ambiguous account names. Currency must match the app currency, with no conversion. `Type` uses `expense`, `income`, `refund` or `transfer`; Destination account is blank for other types. File metadata determines each row's assignment rather than duplicating rows across the selected buttons.

Legacy files with exactly `Date,Details,Category,Cost,Notes more info` remain supported. In the screen, select exactly one account (including Unassigned) and one non-transfer type to assign their rows; a file with no assignment columns cannot infer mixed accounts/types. The codec's legacy API retains its unassigned-expense fallback for existing callers. Supplying accounts to `TransactionCsv.encode` produces the extended format; omitting them preserves the legacy five-column output.

Limits: UTF-8, 5 MiB, 5,000 nonblank rows. Comma/semicolon/tab delimiters, reordered headers, quoted/multiline fields, ISO or day.month.year dates and decimal point/comma are accepted. Two-digit years mean 2000-2099. Export uses BOM, quoted fields, exact app-currency precision (including IQD) and day.month.year across all dates.

Preview before committing; invalid rows prevent import, and the preview identifies each row's type and accounts. New categories are created atomically for non-transfer rows, with existing labels matched case-insensitively. Skip-existing compares date, details, category, cost, notes, currency, type and both accounts as a multiset, preserving repeated purchases. Imported rows are written together, then balances are checked by ledger day for every affected account: same-day income/transfers can fund spending irrespective of file order, but later funding cannot cover an earlier deficit. Blocked outgoing payments, overdraft and currency rules still apply. Any failure rolls back the whole import, including new categories. CSV includes settlement transactions as ordinary expenses/income, but excludes debt balances and their settlement links. Importing those rows does not reduce an outstanding debt automatically. CSV includes transactions, not opening balances, photos, debts, setup, recurrence or full settings; it is not complete backup/restore.

## Current limits and external boundaries

No login, cloud sync, bank integration, analytics backend, budgets, full backup/restore, XLSX import, live exchange-rate service, native OCR or web runtime. Local reminders have the OS/window limitations above. No production signing verification or iOS device validation is implied by debug Android builds. Dependencies and native adapters are mapped in [build/porting](APP_MAP.md#build-export-and-porting).

Private databases, financial workbooks, `/examples`, `/exports` and the original implementation prompt are ignored. Do not use private financial records as test fixtures or log receipt/provider/key contents. Synthetic tests cover behavior without paid Gemini requests.

Category picker Edit opens the Categories management route on the current expense/income kind instead of changing grid taps into edit actions. Back returns to the picker; independently saved renames remain attached to draft selections by stable ID. Management cards use the indexed kind lists and lazy builders; displayed ordinals are list positions, not persisted IDs or ordering controls.

## Overview monthly net savings

Confirmed definition: monthly savings equals income minus spending in the setup currency. Existing `MonthlyLedger.totalsFor(currency)` / `Totals.net` provide the values: refunds reduce spending and transfers are excluded. Opening balances, outstanding debt balances and unposted recurring schedules are not savings transactions. Current-month totals follow Home's transaction-date grouping and are labeled In progress; future months are not offered. This is a monthly flow, not cumulative savings or month-end account wealth. Empty months are zero. Money remains integer minor units; only plotted coordinates use doubles, with full currency precision retained in selected summaries/tooltips. No schema or financial calculation change.


## Native debt settlement and defaults (schema 17)
`currency_exchange_rates` settings JSON maps `from_to` currency enum names to positive decimals (destination major units per one source unit, up to 12 decimals). Inverse/cross calculations preserve exact fractions until final minor-unit rounding. Migration seeds known bank reporting-to-native rates; bank rates remain independent afterward. Settings removes reverse duplicates on save. Foreign debts may be saved without rates, and defaults may be deleted. Missing conversions are excluded from main-currency totals and identified with a prefilled Settings shortcut. Inconsistent data missing a rate shows warnings and is excluded from totals rather than silently treated as valued money.

Outstanding debt/receivable amounts retain native currency; card values and wealth use current shared defaults. Currency/direction cannot change after payments; manual outstanding-balance corrections remain available. Setup debts may use native currencies without a conversion rate.

`settleDebt` accepts native principal, account, exact account-units-per-debt-unit rate, account-currency fee, date and optional transaction ID. Same-currency settlements force rate 1 and fee 0, hiding both fields. Cross-currency principal converts once to account minor units; the account's reporting rate determines the frozen setup-currency ledger amount. Original rate/pair are retained in details/history notes. Changing defaults never rewrites history; unchanged native effects retain prior reporting values and FX snapshots when editing.

Outgoing payments deduct principal plus fee; receipts post gross income and a separate Exchange fees expense, leaving principal minus fee. Incoming fee must be less than principal. Principal, fee and native outstanding balance commit atomically with final historical/future funds validation and blocked-account rules. Editor balance preview replaces prior effects through the selected date; saving is authoritative.

Nonnull-details settlements update native balances explicitly; legacy null-details links keep original app-currency amount editing. Main routes both principal and fee edits to the settlement form; generic bulk edits reject linked native rows. Deleting principal also deletes fee and restores native amount; deleting just fee clears its FK without restoring principal. Debt deletion detaches links and preserves ledger history. CSV exports ordinary ledger rows without settlement links/details and remains unsuitable as a debt backup.


## Optional debt deadlines (schema 18)
Deadline and acknowledgement store local wall-clock ISO strings without UTC offsets, so reminders follow the phone time zone. A reminder is pending when amount > 0, deadline is set and acknowledgement differs from that deadline; it is due when deadline <= local now. Migration adds nullable fields without modifying existing money/links.

Keep/edit acknowledges only the exact currently saved deadline (conditional database update protects changed deadlines), then opens the current debt editor. Cancellation keeps the acknowledgement and outstanding amount. Pay/Receive opens normal settlement without acknowledging; cancellation or partial settlement retains the remaining reminder, full settlement removes it. Changing deadline resets acknowledgement; disabling deadline clears both. No deadline action posts money automatically. Reversing a full payment restores an unacknowledged due balance.

The phone service uses negative debt IDs, original deadline in payload for stale-response rejection, and a separate debt_deadline iOS category / debt_deadlines Android channel. Body taps highlight the debt in the shared inbox; native Keep/Pay actions open their editors after navigation is ready. Future debt and recurring reminders share a chronological maximum of 60 scheduled requests; overdue items remain authoritative in SQLite/inbox. Settings disables phone reminders without deleting due debts. The global bell and inbox re-evaluate due deadlines every minute while mounted.
